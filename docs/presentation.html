Support Ticket Router

Reads customer support emails, classifies them with Claude, and creates Jira tickets. Emails it is unsure about go to a person instead.

Project overview

What the router does

1 · Input

Customer emails as .eml files. The router reads the sender, the subject and the plain-text body.

2 · Classify

Claude reads each email and returns structured fields: category, urgency, a one-line summary, the team, and how confident it is.

3 · Act

A Jira ticket with priority and labels, or the email is held for a person when it is unclear, empty or suspicious.

How it is implemented · 1

The schema is the contract with the model

class EmailClassification(BaseModel):
    category: Literal["account_access", "incident", "billing",
                      "feature_request", "performance", "other"]
        = Field(description=CATEGORY_DEFINITIONS)
    urgency:  Literal["low", "medium", "high", "critical"]
        = Field(description=URGENCY_DEFINITIONS)
    summary:  str = Field(min_length=15, max_length=240)
    route_to: Literal["support", "engineering", "billing", "product"]
    confidence:  Literal["high", "medium", "low"]
    needs_human: bool

    @model_validator(mode="after")
    def validate_route(self):        # billing → billing, ...
    @model_validator(mode="after")
    def low_confidence_needs_human(self):

Literal = a fixed list

Instructor shows the allowed values to Claude. Anything else fails validation and is retried.

Descriptions are prompt

Each field's description is read by the model, so the label definitions live right on the field.

Validators check meaning

They raise an error that is sent back to Claude, so the model can correct itself.

Honest limits and next steps

What this does not prove yet

Limits

  • 21 synthetic emails: one answer moves a field by ~5%
  • Labels and prompt written by the same people
  • Keyword rules can over-hold (e.g. "System: Windows 11" in a body looks like an instruction). Safe, but extra work for people.
  • Escaping and rules reduce injection risk; they do not remove it
  • A validator proves consistency, not truth

Next steps

  • Add real (anonymised) emails, labelled by a second person
  • Decide the team rule for suspicious logins (ticket 013)
  • Add a tune email like 018 (admin change) and fix low vs medium
  • Send held emails to a Jira triage queue instead of a JSON file
  • Run eval/run_eval.py in CI on every prompt change to catch regressions
